# Probe the error range under every expression shape before writing attribution rules

PR #100 derived variable names from MiniJinja's `UndefinedError` range after probing
plain attribute access, whitespace, brackets and parentheses. It never probed an
undefined value piped into a filter. For `{{ steps.first.absent | upper }}` the range
covers `upper`, so the branch reported `unknown variable '{{ upper }}'`. That is the
same misattribution the ticket existed to remove. Two spec review rounds and a Codex
validation all missed it, because each reviewer checked the rules against the probe
table the spec already had.

MiniJinja 2.19 ranges seen so far: attribute access covers `.missing.output` (no
root); a filter receiving undefined covers the filter name; `steps\n.missing` has no
range at all; an unterminated block points past the end of input.

Rule: before specifying how a name is extracted from a parser error location, build
the probe matrix from expression composition, not from the bug report. Cover bare
names, attributes, brackets, parentheses, filters, tests, function calls, whitespace
and newlines, and put undefined values in each argument position. Where extraction
is uncertain, accept only an allowlisted shape and otherwise quote the enclosing
expression, as main's `attributed_variable` does.

How to apply: run the matrix in a scratch crate pinned to the Cargo.lock version.
MiniJinja's span setter is `pub(crate)`, so in-repo tests cannot build an error with
an arbitrary range. Test range handling through a pure helper that takes
`Option<Range<usize>>`, and test the runtime shapes through `interpolate_with_fields`.
