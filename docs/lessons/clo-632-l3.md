# An allowed restatement from an untrusted layer must be stripped, not merged

The first CLO-632 spec let a project value through when it equalled the built-in
default, and then merged it. The spec review showed that this is a downgrade path.
A repo could restate `command = "codex"` to replace a user's pinned `/opt/bin/codex`
with whatever `codex` is first on `PATH`, or restate the default `args` to drop the
user's `-s read-only`. The file passed the check and still changed the effective value.

Decision (user, 2026-09-15): check that the value is an allowed restatement, then
remove every gated key from the project overlay before `deep_merge`, so the lower
layers always decide. Files keep loading, and the untrusted layer can never change a
gated value.

Rule: in a layered config, "allowed" and "takes effect" are separate questions. For
keys an untrusted layer may not control, validation decides whether the file loads.
The merge must still ignore the value.
