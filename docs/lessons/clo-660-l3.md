# Verification commands that pass on failure: four shapes seen in one spec

Revisions 2 and 3 of the CLO-660 spec contained checks that would report success
without testing anything:

1. `git diff --name-only main...HEAD` compares commits only. It ignores staged,
   unstaged and untracked files, and it printed nothing on a dirty tree.
2. `cargo ... | tail` or `| rg` reports the pipe's last command, so a cargo failure
   is lost.
3. `LIVING="a b c"; rg pat $LIVING` word-splits in bash but not in zsh, the user's
   shell, where rg gets one path with spaces and errors. The round-2 reviewer proposed
   the same form.
4. A warning count equal to the baseline can still hide a new warning that replaced an
   old one.

A fifth problem made evidence look missing rather than hiding a failure. The spec kept
logs in the session scratchpad, but the workflow YAML recorded the location as a
`<session scratchpad>` placeholder, so the external validator returned FAIL because it
could not find the logs.

Rule: capture exit codes directly (`cmd > log 2>&1; echo "exit=$?"`). Build change
sets from `git diff --name-only "$(git merge-base main HEAD)"` plus
`git ls-files --others --exclude-standard`. Use arrays (`"${ARR[@]}"`) for path lists.
Compare sorted warning message lines, not counts. Record evidence paths as absolute.

How to apply: before the spec checkpoint, dry-run every evaluation command on the
unedited tree, in the user's shell, and confirm each one's pre-edit result is the one
you expect, including checks that should hit before the fix.
