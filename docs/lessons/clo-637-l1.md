# Replay recorded API data before building a gate on a proposed signal

CLO-637's issue text prescribed the detection signal: poll the Qodo review
comment's `updated_at`. Replaying the recorded GitHub data for PRs #71/#80
before speccing disproved it - the field bumps mid-pass (busy states) and even
10 seconds after merge with no review requested (permalink refresh), so gating
on it reports re-validations that never happened. The signal that actually
worked (the append-only completion comment naming the covered commit) appears
nowhere in the issue; only the replay surfaced it.

Rule: when a task proposes polling a third-party behavioral signal, replay
recorded traffic for both the success and the failure case before writing the
spec - and prefer append-only evidence (`created_at` on a new object naming its
target) over mutable state (`updated_at`, edited bodies). Mutable state changes
for reasons other than the event you care about.

How to apply: fetch the relevant API objects for one PR/run where the event
happened and one where it did not; pin the timestamps in the spec's acceptance
criteria so verification is a replay, not a claim.
