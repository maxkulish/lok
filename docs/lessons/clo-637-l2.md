# jq `contains($var)` with an empty variable is vacuously true - it deletes the condition

CLO-637's new completion-comment path required the comment body to contain the
post-push head SHA. When the `gh api ... --jq .head.sha` lookup fails, the shell
variable is empty, jq's `contains("")` is true for every string, and the
covered-commit check silently vanishes: any fresh matching comment passes the
gate. The failure is invisible in review because the jq reads correctly for the
intended input; it fails open only on the degraded one.

Rule: every variable interpolated into a gate condition needs a shape guard
before the loop, not just a presence guard - a SHA is `^[0-9a-f]{40}$`, not
merely non-empty. Test the gate with each input empty, not only with valid
values; the empty case is where string predicates (`contains`, `startswith`,
`test`) quietly invert from filter to pass-through.

How to apply: for each `--arg x "$X"` feeding a select(), add a pre-poll guard
that rejects malformed `$X` with a message naming the likely upstream failure,
and add a probe with `$X=""` to the verification set proving the gate refuses.
