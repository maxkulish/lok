# `lok init` writes every default key, so "forbid key X in the project file" breaks every generated config

The CLO-632 ticket proposed refusing `command` in the project layer outright. That
would have rejected every file `lok init` ever produced, and lok's own `lok.toml`,
because `init_config` serializes `Config::default()`: all four backends with `command`
and `args`, including `args = []`.

A second trap sits in how presence is detected. Parsing the project file into the
typed `Config` fills omitted fields with serde defaults, so `args` reads as `[]`
whether or not the file wrote it. Presence has to come from the raw `toml::Value`,
while the comparison itself should use typed values.

Rule: a key restriction on a lower-trust layer must accept restatements of the
built-in default (and of the user's resolved value). Presence comes from the raw
TOML, and equality from typed fields.

How to apply: when gating another key or layer, add a test that feeds
`toml::to_string_pretty(&Config::default())` as the project file under a user
override, as `project_repeat_of_builtin_default_keeps_user_value` does.
