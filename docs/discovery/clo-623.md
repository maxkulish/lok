# Discovery: CLO-623 - pr-review-cycle shell snippets executable and tested

## Problem framing

Every lok task that reaches the `pr` phase runs merge gates whose logic
exists only as bash snippets inside two markdown files. Nothing executes,
lints, or tests those snippets, so gate defects survive until a code
reviewer happens to read the prose (PR #71: seven chained findings, two of
them trivially caught by running the code once). Several gates fail open:
empty `gh` responses or unset variables read as success. We want one
tested implementation both files call, with CI enforcement, without
changing the gate semantics the prose documents.

## Existing code

- `.pi/skills/pr-review-cycle.md` (17 bash blocks): steps 1a (installation
  probe + Qodo billing-block detection), 1b (`wait_for_bot_review` helper,
  two delivery shapes), 2 (fail-closed gate on unset `INSTALLED_BOTS`),
  7 (`REPLY_PUSH_TS` window computation with the `null`-string footgun),
  8 (re-review request + poll + new-comment re-check). The prose encodes
  real, verified behavior (two delivery shapes, billing-block notice,
  clock-domain discipline) - this is the spec the script must port.
- `.claude/commands/pr/review.md` (17 bash blocks): Step 9.5 duplicates the
  1b poll and the re-review request almost verbatim; steps 3/9 (fetch,
  reply) are thin `gh api` wrappers fine to keep as prose examples.
- `.pi/scripts/check-schema-parity.mjs` is the only existing first-party
  script under `.pi/scripts/`; there are **no** first-party `.sh` files in
  the repo today and no shell-test harness. CI (`.github/workflows/ci.yml`)
  has no shellcheck job; `CI Gate` (job `ci-gate`) requires
  `build-and-test`, `library-boundary`, `msrv-check`.
- `.pi/orchestrator/phases/pr.md` and its Claude mirror reference the
  skill but hold no review-cycle gate logic themselves (their bash blocks
  are cargo/git operational commands).

Baseline score: **4/10** - the prose is a correct, battle-tested spec, but
as code it is unexecuted, duplicated twice, and proven to drift (PR #71).

## Approaches

### A. Extract to a POSIX shell script + shellcheck + fixture tests (chosen)

One script `.pi/scripts/pr-review-cycle.sh` with subcommands; tests run it
against a fake `gh` on PATH serving recorded JSON fixtures; a new CI job
runs shellcheck + the tests and joins `ci-gate`'s needs.

- Pros: matches the ticket's proposed shape; shell is what the agent
  harness actually runs; zero new build machinery for the markdown
  consumers; fake-`gh` fixture tests are simple and hermetic.
- Cons: shell remains harder to test than Rust; poll loops need
  injectable sleep/clock for fast tests.
- Effort: M. Risk: low-medium (behavioral parity must be proven, not
  assumed - exactly what the fail-closed tests are for).

### B. Move the gates into the lok Rust binary (`lok pr review-wait ...`)

- Pros: real type checking, existing test infrastructure, single cargo
  test gate.
- Cons: the skill spans `gh api` + `jq` filtering that lok does not
  currently do; a new dependency surface (REST/GraphQL client or `gh`
  shell-outs anyway); agents on a stale lok build would run stale gates -
  the markdown snippets at least ship with the repo.
- Effort: L. Risk: medium.

### C. Keep snippets, add a snippet-extraction test harness

Extract ```bash fences from markdown and shellcheck/execute them.

- Pros: no markdown rewrite; tests the exact text agents copy.
- Cons: still two drifting copies; snippets reference ambient variables
  (`$REPO`, `$PR`, helpers) so extraction needs scaffolding; the harness
  itself becomes untested shell.
- Effort: M. Risk: medium-high.

## Choice

**Approach A.** It is the ticket's own proposal, gives one implementation
both consumers call, and the fail-closed fixture tests directly target the
PR #71 failure modes. Approach B would be the stronger end state but is a
separate, larger project; C preserves the duplication that caused it.
