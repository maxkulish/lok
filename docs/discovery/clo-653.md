# Discovery Report: CLO-653 — Config-aware backend cache keying

## Problem Framing

**WHO**: Any host embedding `lokomotiv` more than once in a process — the remem-ai and gcm consolidation that CLO-589 → CLO-593 existed to enable. Single-consumer CLI use is unaffected.

**WHAT today**: `BACKEND_CACHE` is a `HashMap<String, CachedBackend>` keyed by backend name alone (`src/backend/mod.rs:430`). `create_backend` reads the cache at `mod.rs:367` and returns the existing instance on a hit, before ever looking at the `config` argument. The second caller asking for `"ollama"` with a different endpoint or model receives the first caller's instance. Nothing errors and nothing warns.

**WHAT we want**: Cache identity that distinguishes configurations; every reader and writer agreeing on that identity; health probing and warmup behaviour unchanged for the single-consumer case.

**WHY now**: The failure mode is a wrong answer from a working call, and it sits on the critical path for the library extraction whose entire purpose was two-consumers-in-one-process. It was recorded as a standing constraint in `docs/DEPENDENCIES.md` rather than as an issue, which is why no backlog view surfaced it. The crate is not yet published (Phase 13), so the public-API portion of the fix is free today and a semver-major rename-and-yank after publish.

## Existing Code

### The cache and its key

```rust
// src/backend/mod.rs:430
pub static BACKEND_CACHE: OnceLock<RwLock<HashMap<String, CachedBackend>>> = OnceLock::new();
```

`create_backend` (`mod.rs:358-417`) reads by name at line 367, constructs on miss, optionally wraps in `RetryExecutor` when `retry_policy.max_retries > 0`, and inserts by `name.to_string()` at line 405.

### Crate boundary — narrower than it looks

`src/lib.rs` declares exactly one module:

```rust
pub mod backend;   // src/lib.rs:92
```

and `src/main.rs:24` aliases the binary's own module tree:

```rust
pub(crate) use crate::engine as backend;
```

So `backend::get_cached_health` and `backend::Engine` in `main.rs` resolve to `engine.rs`, **not** to the library. `engine.rs`, `workflow.rs` and `conductor.rs` are binary-only. This splits the eight name-keyed sites into two groups with very different change costs.

**Public library API (changing these is a semver break):**

| Site | Shape |
|---|---|
| `backend/mod.rs:430` | `BACKEND_CACHE`, `pub static`, documented in `lib.rs:75-78` |
| `backend/mod.rs:432` | `get_backend_cache()`, `pub fn`, returns the map type |
| `backend/mod.rs:367,405` | `create_backend` read + insert — **signature need not change** |
| `backend/mod.rs:564` | `is_backend_available`, `pub(crate)` — internal despite being in the library |

**Binary-only (free to change):**

| Site | What it does | Config in scope? |
|---|---|---|
| `engine.rs:100` | `warmup_backends` skip-check | yes — iterates `config.backends` |
| `engine.rs:161` | `warmup_backends` write-back, keyed by `backend.name()` | no — key lost inside the future |
| `engine.rs:199` | `get_cached_health(name)`, called from `main.rs:795` | yes — caller iterates `config.backends` |
| `workflow.rs:107` | `codex_unusable_flag_warnings` health read | **no** |
| `workflow.rs:224` | hardcoded `lock.get("ollama")` for model validation | **no** |

Test-only: `engine.rs:184` (`Engine::is_backend_available`, `#[cfg(test)]` — the issue mistakes this for a production call site), `engine.rs:461` (`assert_probed`), and roughly thirty tests that insert or assert on bare name keys.

### Providers do not retain their configuration

```rust
// src/backend/ollama.rs:11
pub struct OllamaBackend { client: Client, base_url: String, model: String }
```

Derived fields only. All five providers call `super::is_backend_available(self.name())` (`ollama.rs:180`, `bedrock.rs:233`, `codex.rs:350`, `claude.rs:324`, `gemini.rs:820`), and none of them holds a `BackendConfig` to key on. `RetryExecutor::is_available` (`retry.rs:146`) delegates to its inner backend, so the wrapper is transparent here.

### `create_backend` callers already hold everything needed

Nine production call sites — `conductor.rs:185`, `engine.rs:108`, `engine.rs:223`, `engine.rs:431`, `workflow.rs:866`, `workflow.rs:1907`, `workflow.rs:2144`, `workflow.rs:2265`, `workflow.rs:2369` — every one of them already has both `backend_config` and `retry_policy` in scope. `create_backend` can compute the key internally and keep its current signature.

### Hashability

Every `BackendConfig` field (`bool`, `Option<String>`, `Vec<String>`, `usize`, `Option<Duration>`, `Option<usize>`, `Option<u64>`) and every `RetryPolicy` field (`usize`, `Duration`, `Duration`) already implements `Eq + Hash`. Deriving `PartialEq, Eq, Hash` on both is mechanical.

### The compensating control

`acquire_test_lock` (`mod.rs:641`, gated on `test` or `test-support`) serialises every test that touches the global. It exists because of this defect and is used at ~15 sites in `engine.rs` alone.

## Approaches

### Approach A: Owned `BackendKey { name, config, retry }` in the process-global (recommended, chosen)

**Summary**: Derive `PartialEq + Eq + Hash` on `BackendConfig` and `RetryPolicy`, introduce a `BackendKey` holding all three values, and change the map to `HashMap<BackendKey, CachedBackend>`. Each provider gains a `key` field populated at construction so `is_available` can look itself up.

**Pros**:
- No hash-collision surface. A collision under a digest key would silently reproduce the exact bug being fixed
- Sidesteps the "stable across runs" requirement the issue states, which is moot for an in-memory cache anyway
- Closes the `RetryPolicy` gap (see Risk 4) that a `BackendConfig`-only key leaves open
- `create_backend` keeps its signature; all nine production callers are untouched

**Cons**:
- One `BackendConfig` clone per cache entry. At ~16 entries this is noise
- Larger keys mean hashing a `Vec<String>` and several `Option<String>` on every lookup, including the hot `create_backend` read

**Effort**: M · **Risk**: Low-medium (concentrated in Risk 1)

### Approach B: `u64` digest of config + retry

**Summary**: What the issue proposes, extended to cover `RetryPolicy`. `BackendKey { name: String, cfg_hash: u64 }`.

**Pros**: Small fixed-size keys, cheaper hashing on the lookup path.

**Cons**: Introduces a collision surface whose failure mode is silently returning the wrong instance — indistinguishable from the bug under repair, and strictly harder to detect because the cache would then look correct by construction. Also inherits the digest-stability question the issue raises.

**Effort**: M · **Risk**: Medium

### Approach C: Host-owned `BackendCache` handle

**Summary**: The embedding host constructs and owns a `BackendCache`; the process-global becomes a lazily-built default for the CLI.

**Pros**: The better long-term library shape, as the issue itself says. Removes global mutable state, which would let `acquire_test_lock` retire and the test suite parallelise.

**Cons**: Breaking change to `create_backend` at all nine production call sites plus `tests/backend_public_api.rs:27`, and a much larger diff through the CLI wiring. Does not remove the need for Approach A's work — a host-owned cache still needs a config-aware key inside it, or the same bug reappears per-handle whenever one host builds two configs.

**Effort**: L · **Risk**: Medium-high

### Approach D: Document harder, fix nothing

**Summary**: Keep the constraint, strengthen the rustdoc, tell consumers to construct at most one instance per name per process.

**Pros**: Zero risk today.

**Cons**: Fails every acceptance criterion, and the cost of the real fix rises sharply the moment the crate is published, because `BACKEND_CACHE`'s type is public and documented.

**Effort**: XS · **Risk**: Low now, high later

## Chosen Approach

**Approach A**, with Approach C recorded as the deliberate deferral it is.

The decisive point against C is that it is not an alternative to A but a superset of it: a host-owned handle still needs config-aware keying inside, so choosing C means doing A's work plus a breaking API migration. Doing A now and C later loses very little, because the second change is mechanical once the key exists.

The decisive point against B is that its failure mode is the failure mode this ticket exists to eliminate.

## Assumptions and Risks

| # | Item | Confidence | How to verify |
|---|---|---|---|
| 1 | **Warmup write-back divergence.** `warmup_backends` reads at `engine.rs:100` with the config map key but writes back at `engine.rs:161` using `backend.name()`. Identical under name keying, divergent under config keying — warmup would insert a second entry and `is_available` would never see a probe. The highest-risk site in the change. | high that it breaks if unaddressed | Thread the `BackendKey` into the future alongside the backend; assert in test that warmup leaves exactly one entry per configured backend |
| 2 | **`workflow.rs:224` and `workflow.rs:107` have no config in scope.** Both are diagnostic reads (model validation, unusable-flag warnings), not instance selection. | high | Open design question — thread config through, or add a by-name scan helper documented as diagnostics-only |
| 3 | **Public break is limited to `BACKEND_CACHE` and `get_backend_cache`.** `engine.rs` and `workflow.rs` are binary-only via the `main.rs:24` alias. | high | `cargo check` on `tests/backend_public_api.rs`; the `library-boundary` CI job |
| 4 | **`RetryPolicy` belongs in the key.** It is derived from `config.defaults` via `get_retry_policy`, which is not part of `BackendConfig`, and it determines whether the instance is `RetryExecutor`-wrapped. | high | Test two configs identical except `defaults.max_retries` |
| 5 | **Deriving `Eq + Hash` on `BackendConfig` compiles.** All field types support it. | high | `cargo check` |
| 6 | **Test-suite churn.** ~30 tests insert or assert on bare name keys and ~15 take `acquire_test_lock`. | medium on volume | Compiler finds every one; the lock stays, since the global remains |

## Baseline Score

**6/10.** The surrounding code is sound — `CachedBackend` unifying instance and health was the right call, the `None`-vs-`Some(unavailable)` distinction for unprobed entries is deliberate and documented, and the lock discipline around cross-backend work is careful. The key itself is the flaw, and it was a knowing tradeoff rather than an oversight.

## Discovery Debt

**One open question**, carried into design: how `workflow.rs:107` and `workflow.rs:224` identify their entries when no config is in scope. Both are diagnostics rather than instance selection, so a by-name scan is defensible, but it must be a named, documented helper rather than an incidental `lock.get(name)` that reads like the old behaviour.

No killer assumptions. The approach is chosen, the constraints came from reading the call sites rather than from estimation, and the one genuine unknown has at least two acceptable answers.
