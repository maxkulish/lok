# Discovery Report: CLO-631 shell-safe workflow interpolation

## Problem framing

Lok workflow authors and operators are affected because dynamic `steps.*` values are rendered into `shell` strings and then passed to `sh -c`. Checked-in review workflows feed model output derived from PRs, designs, and specifications into fixed heredocs or quoted shell fragments; ordinary apostrophes can break some commands, while command substitutions and delimiter collisions can turn data into shell source. The engine already registers a POSIX single-quote `shell_escape` filter, but checked-in workflow files and documentation do not use or require it. This task closes those concrete injection paths and adds a regression gate before more workflows copy the unsafe patterns.

## Existing code

### Rendering and execution path

- `WorkflowRunner::interpolate_with_fields` in `src/workflow.rs` renders `prompt`, `shell`, and `verify` with one MiniJinja `TemplateEngine`.
- `run_shell` in `src/workflow.rs` passes the fully rendered command to `sh -c`; it cannot distinguish literal data from intended shell syntax after rendering.
- `src/template/filters.rs` registers `shell_escape`. It strips NUL bytes, wraps the value in single quotes, and closes, escapes, and reopens the quote around each embedded apostrophe (`'\\''` in the produced shell text). Unit coverage already includes apostrophes, backticks, `$()`, newlines, NULs, and Unicode.
- The existing interpolation test proves only that the filter returns a quoted string. There is no end-to-end shell execution test and no repository policy test.

### Unsafe checked-in shell sites

- `.lok/workflows/design-review.toml`, `spec-review.toml`, and `pre-pr-validation.toml` write reviewer output through public fixed heredoc delimiters. A matching standalone output line terminates the body and exposes following lines as shell.
- `.lok/workflows/design-review.toml` and its shell fixture place health-check output inside literal apostrophes.
- `examples/workflows/full-heal.toml` embeds parsed model fields inside apostrophe-delimited `gh` arguments and heredoc-backed command substitutions.
- `examples/workflows/pick-and-propose.toml` and `review-pr.toml` construct comments with fixed heredocs containing model fields.
- `examples/workflows/rework-pr.toml` passes `headRefName` to `git` unquoted and embeds a model summary in commit and comment shell strings.
- `examples/workflows/review-pr.toml` has the highest-risk boundary: a second model is prompted to generate arbitrary `gh issue` shell commands, and `run_followups` executes the response verbatim.
- Shell-only TOML fixtures repeat unsafe quoting patterns, so a repository-wide scanner must either fix them or exempt them. Fixing them makes the fixtures demonstrate the expected authoring style.
- README's introductory workflow example teaches the unsafe apostrophe pattern; `docs/guides/lok-setup-guide.md` documents variables but not shell escaping.

### Constraints and prior lessons

- `docs/lessons/clo-625-l3.md`, `l4.md`, and `l6.md` show that shell snippets must be executed under the real shell and that apparently harmless command composition can fail closed/open differently than expected. The runtime regression therefore runs through `cargo run --bin lok`, not only string comparison.
- `docs/lessons/clo-655-l2.md` requires focused workflow module tests to use `--bin lok`; `cargo test --lib` can pass with zero relevant tests.
- `docs/lessons/clo-655-l5.md` requires guarded references to `when`-skipped steps. Rewriting output persistence must retain the existing MiniJinja defined/success guards.
- `docs/lessons/clo-656-l3.md` requires checking sibling worktrees and open PRs before work starts. No sibling worktree, open PR, or existing commit claims CLO-631.
- `docs/lessons/clo-656-l4.md` requires `cargo run --bin lok` because this package has multiple binaries.

## Baseline score

**8/10.** The correct escaping primitive, common rendering engine, shell-only integration harness, and TOML parser already exist. No engine rewrite is needed. The missing pieces are safe shell composition at each call site, a policy scanner, a hostile-content workflow, and author documentation. The main design risk is preserving review-file formatting and issue-creation behaviour while removing heredocs and generated commands.

## Approaches

### A. Explicit escaping plus structural shell rewrites and a static gate (chosen)

Apply `shell_escape` to every dynamic step value used as shell data. Replace heredoc writes with `printf` complete arguments, replace generated follow-up commands with validated JSON iteration, and add a TOML-aware repository test.

**Pros**
- Uses the existing, tested defence and keeps engine behaviour compatible.
- Preserves follow-up issue creation without granting a model command authority.
- Makes unsafe additions fail in ordinary CI with actionable file/step diagnostics.

**Cons**
- Every shell composition site needs careful restructuring; adding a filter inside existing quotes is not sufficient.
- Static analysis enforces an authoring convention rather than proving all possible shell safety properties.
- JSON validation for follow-ups adds `jq` as a runtime expectation to an example that already depends on `gh`.

**Effort:** M  
**Risk:** Medium

### B. Automatically escape `steps.*` when rendering every shell field

Change the engine so values interpolated into `shell` are escaped by default, with an opt-out for intentional shell fragments.

**Pros**
- Safer default for future workflow authors.
- Centralizes policy in the execution engine.
- Could protect workflows outside this repository.

**Cons**
- MiniJinja receives whole shell templates, not a shell AST; the renderer cannot know whether a value is already in quotes, part of a larger word, or intentionally structured.
- Changes semantics for every existing user workflow and requires an unsafe/raw escape hatch.
- Does not by itself solve fixed heredoc delimiters or model-authored command execution cleanly.

**Effort:** L  
**Risk:** High

### C. Remove the dangerous example steps and minimally escape the remaining sites

Delete `create_followups`/`run_followups`, remove or simplify affected autonomous examples, and apply escaping only where functionality remains.

**Pros**
- Smallest security surface and least shell complexity.
- Eliminates generated-command execution outright.
- Low implementation risk.

**Cons**
- Regresses documented example functionality rather than repairing it.
- Does not establish a structured pattern for safely turning model JSON into CLI calls.
- Still needs a scanner and documentation to prevent recurrence.

**Effort:** S  
**Risk:** Low

## Chosen approach

Choose **Approach A**. It preserves the useful behaviour while making the trust boundary explicit: models produce data, a deterministic shell step validates that data, and `gh` receives quoted arguments. Engine-wide automatic escaping is deferred because it would be a compatibility change without enough shell-context information.

For `review-pr`, remove the command-generation step entirely. Extract and JSON-encode the synthesis result's parsed `followups` array, pass it as one escaped value to a shell step, validate the full array and label allowlist with `jq` before side effects, then create each issue from quoted fields.

## Discovery debt

None. The implementation can verify the exact shell and TOML-parser mechanics locally. A broader safe-by-default engine mode is a separate compatibility feature, not unknown work required by CLO-631.
