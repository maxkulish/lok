# Discovery Report: CLO-638 — MSRV CI Gate

## Problem Framing

**WHO**: Anyone who builds `lokomotiv` from source or consumes it from crates.io on a Rust toolchain older than the declared MSRV.

**WHAT today**: `Cargo.toml` declares `rust-version = "1.80"` but no CI job builds against it. The local toolchain is 1.95, `ci.yml` uses runner-stable, and no job pins a specific version. The claim is unverified — any API stabilised after 1.80 compiles clean on every machine that touches this repo and breaks only for a consumer on an older toolchain.

**WHAT we want**: A CI job that builds the crate against the declared `rust-version`, fails when code or dependencies need a newer toolchain, and is wired into the `CI Gate` required check so it cannot be ignored.

**WHY now**: CLO-633 prescribed `floor_char_boundary` (stable since 1.91) which would have passed every CI gate and first failed for a crates.io consumer after Phase 13 publishes. The gap was caught by a human reading stabilisation versions, not by a control. CLO-638 was filed as a follow-up.

## Existing Code

### Cargo.toml (`rust-version = "1.80"`)

Line 4 of `Cargo.toml`:
```toml
rust-version = "1.80"
```

This is the only MSRV declaration in the project. No `[package.edition]` override, no `rust-toolchain.toml` file, no `rust-toolchain` file.

### CI workflow (`.github/workflows/ci.yml`)

The `build-and-test` job installs the runner's default stable toolchain:
```yaml
- name: Install Rust toolchain
  run: rustup component add rustfmt clippy
```

No toolchain version is pinned. The `library-boundary` job does the same. Neither job tests against the declared MSRV.

The `CI Gate` job aggregates `build-and-test` and `library-boundary`:
```yaml
ci-gate:
  name: CI Gate
  needs: [build-and-test, library-boundary]
```

### Dependency chain driving the MSRV

The actual minimum Rust version is **1.83**, not 1.80. The constraint comes from transitive dependencies:

```
lokomotiv
  └── reqwest v0.12.28
        └── url v2.5.8
              └── idna v1.1.0
                    └── idna_adapter v1.2.1 (requires 1.82)
                          └── icu_collections v2.1.1 (requires 1.83)
                          └── icu_locale_core v2.1.1 (requires 1.83)
                          └── icu_normalizer v2.1.1 (requires 1.83)
                          └── icu_properties v2.1.2 (requires 1.83)
                          └── icu_provider v2.1.1 (requires 1.83)
```

The ICU4X packages (v2.1.x) are the hard floor at **1.83**. No source code in `src/` uses any post-1.83 API — the constraint is purely from the dependency tree.

### Verification results

| Toolchain | `cargo check --locked --all-targets` | Notes |
|-----------|--------------------------------------|-------|
| 1.80.0 | ❌ Fails | ICU deps require 1.83 |
| 1.82.0 | ❌ Fails | ICU deps require 1.83 |
| 1.83.0 | ✅ Passes | Clean build |
| 1.95.0 (local) | ✅ Passes | Current stable |

### No `rust-toolchain.toml` or `rust-toolchain` file

The project does not pin a toolchain for local development. This is fine — the CI job will be the MSRV gate.

## Approaches

### Approach A: Raise MSRV to 1.83 + add CI gate (recommended)

**Summary**: Update `rust-version` to `"1.83"` in `Cargo.toml`, add a CI job that builds against 1.83, wire into `CI Gate`.

**Pros**:
- Honest about the real floor — the declared MSRV matches what actually builds
- Simple implementation: one `Cargo.toml` change + one CI job
- No dependency pinning or version freezing

**Cons**:
- Raises the support promise from 1.80 to 1.83 (affects consumers on older toolchains)
- 1.83 was released 2024-11-26, so it's still relatively recent

**Effort**: S (one Cargo.toml edit + one CI job + one proof test)
**Risk**: Low

### Approach B: Pin older deps to keep MSRV at 1.80

**Summary**: Downgrade `url` to v2.5.0 and `idna` to v0.5.0 (pre-ICU4X) to avoid the ICU dependency chain, keeping MSRV at 1.80.

**Pros**:
- Preserves the 1.80 MSRV promise
- No change for consumers on older toolchains

**Cons**:
- Freezes `url` at v2.5.0 (2023-11-22), missing security fixes and improvements
- `reqwest` may itself bump its MSRV in future releases, requiring repeated pinning
- Complex dependency resolution — may conflict with other crates' version requirements
- Fragile: a `cargo update` could pull in newer ICU deps and silently break the MSRV again

**Effort**: M (dependency research + pinning + testing + ongoing maintenance)
**Risk**: Medium (dependency conflicts, missed security patches)

### Approach C: Use `cargo-msrv` to discover the floor, then decide

**Summary**: Run `cargo-msrv` to programmatically find the minimum Rust version, then choose between A and B based on the result.

**Pros**:
- Automated discovery, no manual bisecting
- Produces a reproducible result

**Cons**:
- `cargo-msrv` is another tool to install and maintain
- The result will still be 1.83 (ICU deps are the hard floor), so this just adds a step
- Adds CI complexity for marginal benefit

**Effort**: S (one-time tool run)
**Risk**: Low (but adds no value over the manual verification already done)

## Chosen Approach

**Approach A: Raise MSRV to 1.83 + add CI gate.**

The manual verification is definitive: 1.80 and 1.82 both fail, 1.83 passes. `cargo-msrv` would produce the same result. Pinning older deps (Approach B) would freeze `url` at a 2023 version and create ongoing maintenance burden for no real benefit — 1.83 is a reasonable floor for a crate published in mid-2026.

The implementation will:
1. Update `rust-version` in `Cargo.toml` from `"1.80"` to `"1.83"`
2. Add an `msrv-check` CI job that installs 1.83 and runs `cargo check --locked --all-targets`
3. Wire the job into `CI Gate`'s `needs` list
4. Add a deliberate post-MSRV API usage to prove the gate catches it (then revert)

## Baseline Score

**7/10** — The existing code is well-structured and the CI workflow is clean. The only gap is the missing MSRV verification. No rewrite needed.

## Discovery Debt

None. The floor is definitively 1.83, the approach is clear, and the implementation is straightforward.
