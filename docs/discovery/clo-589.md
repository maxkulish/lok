# Discovery: CLO-589

## Problem framing

- **Who is affected:** Internal/external downstream consumers of lok that need a reusable backend abstraction (including the documented `remem-ai` fork path) are currently blocked by an undocumented boundary decision and risk consuming CLI internals.
- **Current behavior:** The backend abstraction lives in `src/backend/*` under binary-centric ownership, with no project ADR recording where the public/library boundary should be drawn.
- **Desired behavior:** Record a definitive extraction shape that downstream consumers can implement against, with a clear split between `lokomotiv` library API and binary-only orchestration logic.
- **Why now:** This is the upstream decision needed before starting actual extraction/migration work in follow-on tasks (`CLO-590`), and the issue explicitly requests this as an entry-point contract so no later team re-litigates the same choices.

## Existing code

`CLO-589` is a decision-only ticket; existing code observations:

- `src/backend/mod.rs` is the central backend API and orchestration entry for CLI usage:
  - `Backend`, `BackendError`, `TokenUsage`, `QueryOutput`, and `QueryResult` are already exported as stable types.
  - Core helpers such as `create_backend`, `create_claude_backend`, `get_backends`, `run_query`, `run_query_with_config`, `list_backends`, `Engine`, `print_verbose_header`, and `print_verbose_timing` are implemented and consumed by CLI/task paths.
  - Backend constructors currently operate on `crate::config::BackendConfig`, while orchestration wrappers (`run_query`, `run_query_with_config`, `get_backends`) accept `crate::config::Config`.
- `src/config.rs` defines `Config` as a large top-level binary config root with fields for `conductor`, `cache`, `tasks`, `roles`, `teams`, etc., while `BackendConfig` and `Defaults` are leaf structs.
  - `Config` references `cache::CacheConfig` and role structs, making it unsuitable as the sole extracted abstraction boundary.
- `src/backend/context.rs` exposes `StepContext` with model/timeout fields and other call metadata, showing an existing coherent backend runtime interface.
- `Cargo.toml` currently defines only `[[bin]]` targets (`lok` and `lokomotiv`) and no `[lib]` section yet.
- No existing ADR directory was present; this task introduces `docs/adrs/` usage per `/adr` direction.

Baseline score: **8 / 10** (interface is mostly coherent, but module/package boundaries are currently undocumented and unbounded).

## Approaches

### Approach A (selected): Decision-only ADR + boundary freeze in repo docs
- Record final library shape and boundaries now, without moving code yet.

Pros:
- Fast, low-risk, and directly satisfies ticket scope.
- Avoids premature refactor before follow-on extraction ticket defines exact implementation plan.
- Prevents team drift on `Config` coupling by recording explicit rule set early.

Cons:
- Does not reduce coupling risk by itself; actual extraction still happens later.
- Consumers still cannot start implementation until next ticket applies the boundary.
- Requires discipline to keep ADR as source-of-truth.

Effort: S
Risk: low

### Approach B: Split + implement library/crate extraction in the same ticket
- Refactor `Cargo.toml` to add library surface (or create `lok-backend`) and migrate code boundaries in one pass.

Pros:
- Immediate usable extraction artifact.
- Faster path to downstream integration for dependent consumers.

Cons:
- Large surface-area change in a ticket scoped for architectural record only.
- High chance of accidental coupling through `Config`/`cache`/`roles` leakage.
- Harder to audit and review because architectural and refactor work are mixed.

Effort: L
Risk: high

### Approach C: Keep status quo and defer to ad-hoc downstream decisions
- Perform no repository ADR and let each consumer infer desired boundary independently.

Pros:
- No repository work now.

Cons:
- Guaranteed inconsistency/risk with conflicting boundary contracts.
- `CLO-590` cannot start with a stable contract.
- Loses explicit versioning/feature-exposure decisions.

Effort: S
Risk: high

## Decision

Chosen approach: **Approach A (decision-only ADR + boundary freeze)**.

Reason: This task is explicitly an entry-point ADR gate and not a migration ticket; it is safer and cleaner to lock the package boundary and coupling rationale first, then execute extraction in follow-on tickets.

## Assumptions and risks

- No PRD section exists in prior issue artifact, so a PRD has been created at `docs/prds/clo-589-backend-library-shape.md`.
- `Config` must stay on the binary side because moving it would import cache/role/conductor responsibilities and create coupling complexity for this extraction.
- `bedrock` should remain feature-gated in `lokomotiv` and exposed to external consumers via crate feature flags.
