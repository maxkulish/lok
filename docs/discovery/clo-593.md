# Discovery Report: CLO-593

**Task:** Extract lok's Backend abstraction into a consumable library target.  
**Linear:** [CLO-593](https://linear.app/cloud-ai/issue/CLO-593/extract-loks-backend-abstraction-into-a-consumable-library-target)  
**Branch:** `feat/clo-593-extract`  
**PRD:** `docs/prds/clo-593-extract-lok-backend-lib.md`

## Problem framing

`lok` has a hardened, multi-provider LLM backend layer (`claude`, `codex`, `gemini`, `ollama`, optional `bedrock`) that is currently trapped inside a binary-only package. The same abstraction already exists in `gcm` and is needed by an upcoming `remem` fork. Because the `lokomotiv` package declares only `[[bin]]` targets, no other crate can reuse the implementation; downstream projects are forced to copy or rewrite it, which produces divergent behaviour per provider. We want to expose the backend module as a library while keeping the existing binaries and test suite intact, so `gcm` and `remem` can build on a single, tested backend layer.

## Existing code

The relevant code lives in `/Users/mk/Code/orchestrator/lok` at `main @ 796154d`.

- `src/backend/` is ~7,350 lines across `mod.rs`, `gemini.rs`, `codex.rs`, `claude.rs`, `codex_event.rs`, `retry.rs`, `ollama.rs`, and `bedrock.rs` (behind the `bedrock` feature).
- The public surface is the `Backend` trait in `src/backend/mod.rs`:
  - `fn name(&self) -> &str`
  - `async fn query(&self, ctx: StepContext<'_>) -> Result<QueryOutput, BackendError>`
  - `fn is_available(&self) -> bool`
  - `async fn health_check(&self) -> Result<HealthStatus, BackendError>` (default impl)
- `BackendError`, `QueryOutput`, `TokenUsage`, `QueryResult`, `RetryPolicy`, `HealthStatus`, `Message`, `Role`, `SandboxMode`, `StepContext`, and `StepOptions` live in `src/backend/`.
- `Engine::warmup_backends`, `get_backends`, `run_query`, `run_query_with_config`, `list_backends`, `create_backend`, and `step_context_for_backend` are orchestration helpers that live in `src/backend/mod.rs` but operate on lok's full `Config`.
- Coupling outside `src/backend/` is very low. Production references are:
  - `crate::config::BackendConfig` in `claude.rs`, `codex.rs`, `gemini.rs`, `ollama.rs`, `bedrock.rs`, and `mod.rs`.
  - `crate::config::Config` and `crate::config::Defaults` in `mod.rs`.
  - One `crate::utils::canonicalize_async` call in `mod.rs:run_query_with_config`.
- `BackendConfig` is a plain, deserializable struct with backend-only fields (`command`, `args`, `model`, `api_key_env`, `timeout`, `max_retries`, `retry_delay_ms`, `enabled`).
- `Config` mixes orchestration concerns (`conductor`, `cache`, `tasks`, `roles`, `teams`) with backend configuration and should not leak into the library.
- `StepContext` carries fields that are natural for a query (`prompt`, `history`, `model`, `cwd`, `schema`, `options`, `timeout`) alongside orchestration/file-edit fields (`apply_edits`, `sandbox`). The latter two are worth auditing before finalising the public API.

**Baseline score:** 7/10 — the backend code is cohesive and lightly coupled, but it is currently a binary-only module and needs a config boundary and a public API audit before it can be safely consumed.

## Approaches identified

### Approach A: add a `[lib]` target to the existing `lokomotiv` package

Introduce `src/lib.rs` that re-exports `backend::*`, move `BackendConfig` and retry defaults into the library, leave `Config` in the binary crate, and update the two binaries to import through the public API.

- **Pros:** Minimal Cargo/workspace changes; one package, one version, one crates.io entry; existing CI and publishing keep working; far less disruptive than a workspace split.
- **Cons:** Library consumers still compile the full dependency set declared in `Cargo.toml`, including some CLI-only crates (`clap`, `indicatif`, etc.); less clean separation than a dedicated crate.
- **Effort:** M
- **Risk:** low

### Approach B: split into a Cargo workspace with a dedicated `lok-backend` crate

Create a workspace root, move `src/backend/` into `lok-backend/src/`, make `lokomotiv` depend on `lok-backend`, and publish the backend crate independently.

- **Pros:** Cleanest boundary; consumers do not pull CLI-only dependencies; independent versioning is possible; easier to enforce that orchestration types stay out.
- **Cons:** More initial setup (workspace `Cargo.toml`, two crates, workspace publishing); changes the repository layout more deeply.
- **Effort:** M–L
- **Risk:** medium

## Chosen approach

**Approach A: add a `[lib]` target to the existing package.**

Reason: the handoff and issue both list this as the default unless independent versioning matters, and no such requirement is stated. It delivers a reusable library with the smallest surface change and preserves the existing package identity, CI, and publishing flow. A future workspace split remains possible if dependency weight becomes a problem.

## Discovery debt

None. The coupling points are identified, the test baseline is known (1,356 tests across 6 suites), and the crate-shape decision is ready to be recorded as an ADR in the design phase.
