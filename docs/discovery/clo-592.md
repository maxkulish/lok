# Discovery Report: CLO-592

**Task:** Make the backend library consumable from crates.io with rustdoc, feature docs and a publish dry-run.  
**Linear:** [CLO-592](https://linear.app/cloud-ai/issue/CLO-592/make-the-backend-library-consumable-from-cratesio-with-rustdoc-feature)  
**Branch:** `feat/clo-592-crates`  
**PRD:** N/A — the Linear issue body is the PRD (see `## Scope` and `## Acceptance Criteria`)

## Problem framing

A developer who finds `lokomotiv` on [docs.rs](https://docs.rs/lokomotiv) today cannot wire a backend into their own program from the documentation alone. The crate is published and the docs.rs plumbing exists (`[package.metadata.docs.rs] all-features = true`), but the content is missing: the crate-level rustdoc is a single paragraph, no working example exists, and the four Cargo features (`default`, `cli`, `bedrock`, `test-support`) are undocumented. A consumer wanting the library without terminal dependencies must discover `default-features = false` by reading `Cargo.toml` — nothing in the docs tells them. The README covers only CLI usage. Meanwhile, the `cargo publish --dry-run` has never executed because the publish workflow asserts `CARGO_TOKEN` is set before reaching the dry-run step, and no such secret exists on this repository. The workspace-split window closes at publish time, so the pre-publish decision about whether to split must be recorded before this ticket ships. CLO-591 just merged, settling the public API surface — this is the moment to document it before the next release bakes in the current state.

## Existing code

### Library surface (`src/lib.rs`)

The library re-exports the backend public API under `#![deny(missing_docs)]`:

```rust
pub mod backend;
pub use backend::{
    create_backend, Backend, BackendConfig, BackendError, ClaudeBackend, CodexBackend,
    GeminiBackend, HealthStatus, Message, ModelInfo, OllamaBackend, QueryOutput, RetryDefaults,
    RetryExecutor, RetryPolicy, Role, SandboxMode, StepContext, StepOptions, TokenUsage,
    DEFAULT_TIMEOUT, NO_TIMEOUT, RETRY_LOG_TARGET,
};
#[cfg(feature = "bedrock")]
pub use backend::BedrockBackend;
```

### Cargo features (`Cargo.toml`)

Four features, only one documented (in the Cargo.toml comment):

| Feature | Dependencies | Purpose |
|---------|-------------|---------|
| `default` | `["cli"]` | On by default; pulls terminal deps |
| `cli` | `indicatif, colored, clap, chrono, dirs, futures, minijinja, sha2, env_logger` | Everything the `lok` binaries need and the library does not |
| `bedrock` | `aws-config, aws-sdk-bedrockruntime` | AWS Bedrock backend |
| `test-support` | (none) | Test helpers (`StubBackend`, `acquire_test_lock`, etc.) |

### Binary targets

Three binary targets, all behind feature gates:
- `lok` (requires `cli`) — main CLI binary
- `lokomotiv` (requires `cli`) — alias binary
- `silence_probe` (requires `test-support`) — spawned by tests to prove the library is silent

### Publish workflow (`publish.yml`)

The workflow accepts a tag via `workflow_dispatch`, asserts the tag matches `Cargo.toml` version, then asserts `CARGO_TOKEN` is set (exits 1 if not), then runs `cargo publish --dry-run --locked`. The token assertion blocks the dry-run because no `CARGO_TOKEN` secret exists on this repository. The workflow header documents this and notes that `CARGO_TOKEN` is not the variable cargo reads (cargo reads `CARGO_REGISTRY_TOKEN`).

### Library-boundary CI job

The `library-boundary` job in `ci.yml` enforces:
1. Library builds without CLI features (`--no-default-features`)
2. No CLI dependency reaches a library consumer (exact-name dependency tree check)
3. Library writes nothing to the terminal (grep for `println!`/`eprintln!` in `src/backend/`)
4. Tests pass with `--no-default-features`
5. Clippy passes with `--no-default-features`
6. Public API is fully documented (`RUSTDOCFLAGS='-D missing_docs' cargo doc`)
7. Binaries install with no extra flags

### Current documentation state

- `cargo doc --all-features` emits 2 warnings (private intra-doc links to `is_backend_available` and `HEALTH_TTL_ENV`)
- Crate-level rustdoc (`src/lib.rs`): one paragraph, no working example
- `BackendConfig`: documented with field-level docs
- `BackendError`: documented with variant-level docs
- `StepContext`: documented with field-level docs
- `HealthStatus`: documented with field-level docs
- `BACKEND_CACHE`: documented with the process-global constraint
- Features: undocumented in rustdoc (no `#[doc(cfg(...))]` or feature doc comments)
- README: CLI-only, no library section

### Key constraints

1. **`BACKEND_CACHE` is keyed by backend name alone** — two consumers in one process with different configs share an instance. Documented but not fixed.
2. **The lib/bin boundary is convention, not compiler-enforced** — the `library-boundary` CI job is the compensating control.
3. **`repository` and `homepage` point at `github.com/ducks/lok`** — needs CLO-609 before any real publish.
4. **`[dev-dependencies]` has a self path-dependency** — `lokomotiv = { path = ".", default-features = false, features = ["test-support"] }`. Unusual shape; `cargo publish` must accept it.

**Baseline score:** 7/10 — the library target exists, the public API is settled, and `#![deny(missing_docs)]` is active. But documentation content is sparse, features are undocumented, the README lacks a library section, and the publish dry-run is blocked.

## Approaches identified

### Approach A: Documentation-only pass

Write crate-level rustdoc with a working example, document every public type, document all four features, add a library section to the README, and fix the two rustdoc warnings. No changes to the publish workflow or CI.

- **Pros:** Fastest path to ship; no risk of breaking CI or the publish pipeline; addresses the core user-facing gap.
- **Cons:** The publish dry-run remains blocked; the `CARGO_TOKEN` gate is not resolved; the pre-publish workspace-split decision is not recorded.
- **Effort:** S
- **Risk:** low

### Approach B: Documentation + publish workflow fix

Same as A, plus move the `CARGO_TOKEN` assertion after the dry-run step so `cargo publish --dry-run --locked` can actually execute. Record the pre-publish workspace-split decision in the docs.

- **Pros:** All acceptance criteria met; the dry-run validates the packaging shape (including the self path-dependency); the workspace-split decision is explicit.
- **Cons:** Slightly more scope; requires understanding the publish workflow's intent.
- **Effort:** M
- **Risk:** low

### Approach C: Full sweep

Same as B, plus document the `BACKEND_CACHE` process-global constraint in the crate-level rustdoc (if still unfixed), add `#[doc(cfg(...))]` annotations to feature-gated items, and add a `cargo doc --all-features` check to CI.

- **Pros:** Most thorough; leaves no documentation debt; the constraint is visible to consumers.
- **Cons:** More scope; `BACKEND_CACHE` documentation already exists on the item itself; `#[doc(cfg(...))]` may require additional cfg attributes.
- **Effort:** M
- **Risk:** low

## Chosen approach

**Approach B: Documentation + publish workflow fix.**

Reason: it meets every acceptance criterion in the Linear issue. The publish dry-run is the only acceptance criterion that cannot be met from documentation alone, and the token assertion is the only thing blocking it. Moving the assertion after the dry-run is a mechanical change that does not weaken the security posture (the assertion still fires before any real publish). The pre-publish workspace-split decision is a documentation item that belongs in the same pass. Approach C's additions (BACKEND_CACHE docs, `#[doc(cfg(...))]`) are either already done or are polish that can be deferred.

## Discovery debt

None. The scope is well-defined by the issue's acceptance criteria, and the chosen approach covers all of them.
