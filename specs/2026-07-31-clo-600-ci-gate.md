# Spec: Make lok's CI a real gate - green main, required check, hardened workflows

**Created**: 2026-07-31
**Revised**: 2026-07-31 (rev 2, after external review; verdict moved APPROVE_WITH_SUGGESTIONS -> REVISE -> revised)
**Linear**: [CLO-600](https://linear.app/cloud-ai/issue/CLO-600)
**Estimated scope**: M (7 files, 8 sub-tasks)
**Reference**: `~/Code/gcm/.github/workflows/` (ci.yml, release.yml)

## 1. Problem Statement

CLO-600 was filed on 2026-07-26 against a repo whose GitHub Actions had never
dispatched: all three repo-owned workflows reported 0 runs for all time, so no PR had
ever been validated remotely. That dispatch failure is **already resolved**. Actions was
activated in the repo's Actions tab and lok has since produced six repo-owned runs
(`30222596040` through `30223254125`), covering both `push` to `main` and
`pull_request`. Acceptance criteria 1, 2 and 4 of the Linear issue are therefore
satisfied by history, and no further investigation of dispatch is needed.

What the first six runs exposed is that the gate is not yet trustworthy.

**main is red.** Run `30223254125` (merge of PR #63 to `main`) failed on
`backend::gemini::tests::gemini_health_check_version_timeout`, at
`src/backend/gemini.rs:1278`:

```
assertion failed: status.diagnostic.unwrap().contains("timed out")
test result: FAILED. 149 passed; 1 failed
```

The test writes `#!/bin/sh\nsleep 10\n` via `write_exec_script`
(`src/backend/mod.rs:518`), sets `version_probe_timeout` to 200ms, and expects
`probe_version` (`src/backend/gemini.rs:578`) to hit the `tokio::time::timeout` arm,
which produces `"opencode --version timed out after 200ms"`. `health_check`
(`src/backend/gemini.rs:822`) wraps any probe error as `"Version probe failed: {e}"`, so
**every** probe failure mode produces a diagnostic and `available: false` - only the
substring distinguishes them. The assertion carries no message, so the CI log records
that the substring was absent but not what the diagnostic actually said. The cause is
therefore not established, only narrowed.

The leading hypothesis is `ETXTBSY`. Run `30222596040` failed eight tests of exactly this
family with that error, and commit `4c13c7c` fixed the version where the test's own
`NamedTempFile` was still open at `execve`. A second window survives that fix:
`write_exec_script` holds a write handle between `NamedTempFile::with_suffix` and
`into_temp_path()`. A `fork` from another test thread inside that window inherits the
descriptor, and `O_CLOEXEC` does not close it until the child's own `execve`, so a
concurrent `execve` of the script can still find a writer and fail with "Text file busy".

**Serialisation is already failing to contain that race, and the inventory matters.**
Verified in the tree at `fad3e91`:

| Site | Writes+execs a script | Lock held |
| -- | -- | -- |
| `src/backend/gemini.rs:1233` (`..._success`) | yes | `acquire_test_lock` (`:1232`) |
| `src/backend/gemini.rs:1267` (`..._version_timeout`) | yes | **none** - this is the failing test |
| `src/backend/gemini.rs:1284` (`..._bad_exit`) | yes | `acquire_test_lock` (`:1283`) |
| `src/backend/gemini.rs:1302` (`..._no_auth`) | yes | `acquire_test_lock` (`:1301`) |
| `src/backend/codex.rs:836, 855, 869, 887` | yes (4 tests) | **none** |
| `src/backend/mod.rs:543` (helper's own test) | yes | **none**, and it is a sync `#[test]` |
| `src/engine.rs:1397` | yes | `acquire_test_lock` (`:1394`) |
| `src/backend/claude.rs:640, 666` (`setup_mock_claude`) | yes, its own mock binary | **`PATH_LOCK`** (`:491`) - a *different* mutex |

Two facts follow. Six script-executing tests hold no lock at all, and `claude.rs`
serialises on a second mutex that does not interoperate with `TEST_MUTEX`, so even a
complete sweep of `acquire_test_lock` would leave the claude family forking freely
alongside it. Extending the lock is therefore containment that must be re-established
every time someone adds a subprocess test - and it cannot be proven, only sampled.

**No required check.** `gh api repos/maxkulish/lok/branches/main/protection` returns 404
and `gh api repos/maxkulish/lok/rulesets` returns `[]`. Nothing prevents a merge while CI
is red or still running.

**The workflows are thin next to gcm's.**

| Gap | lok today | gcm |
| -- | -- | -- |
| OS coverage | `ubuntu-latest` only | `ubuntu-latest` + `macos-latest` matrix |
| Reproducible deps | no `--locked` anywhere | `--locked` on test and build |
| Optional features | `bedrock` never compiled in CI | n/a (no features) |
| Job layout | 3 jobs, cargo cache restored twice | 1 job, one cache |
| Release targets | `x86_64-unknown-linux-gnu` only | 4 targets, native runners |
| Tag safety | none | tag format + `Cargo.toml` version assertion |
| Artifacts | bare binary | tarball + `.sha256`, `if-no-files-found: error` |
| Release action | `softprops/action-gh-release@v1` | `@v2` |
| Binary smoke test | none | `--version` and `--help` on the built binary |

`publish.yml` is worse than thin, it is unreachable. The repo has no Actions secrets at
all (`gh secret list -R maxkulish/lok` returns empty), so `secrets.CARGO_TOKEN` is unset;
and independently, a release created by `release.yml` through the default `GITHUB_TOKEN`
does not emit events that start further workflow runs, so `on: release: [published]` can
never fire from lok's own pipeline.

Two divergences from gcm are forced by lok's dependencies and are decided in §3: lok's
`reqwest` keeps default features, so its TLS is `native-tls`/OpenSSL and gcm's static
musl targets are not available for free; and `softprops/action-gh-release` has moved to
`v3.0.2` (node24), so gcm's `@v2` is the stale reference, not the target.

## 2. Acceptance Criteria

- [ ] AC-1: Every assertion on a `HealthStatus.diagnostic` in the codex and gemini probe
      tests prints the observed diagnostic on failure.
- [ ] AC-2: The cause of `gemini_health_check_version_timeout` failing on Linux is
      established from a captured diagnostic string, quoted verbatim in the PR
      description, and fixed. If the evidence contradicts the `ETXTBSY` hypothesis, the
      recorded cause is the observed one.
- [ ] AC-3: A Linux-only regression test constructs the inherited-write-descriptor
      interleaving deterministically (write handle open -> spawn a child that inherits it
      -> close the parent handle -> exec the script) and passes with the fix in place. It
      is `#[cfg(target_os = "linux")]` and must fail against the pre-fix helper.
- [ ] AC-4: The **complete** unit suite - not a filter over the exec-script family - runs
      20 consecutive times on a Linux runner under default parallelism with zero
      failures, evidenced by a linked run. Filtering is forbidden here precisely because
      the competing subprocess tests are what create the race.
- [ ] AC-5: `ci.yml` runs on `ubuntu-latest` and `macos-latest`, and on both executes
      `cargo fmt --check`, `cargo clippy --locked --all-targets -- -D warnings`,
      `cargo test --locked`, `cargo clippy --locked --all-targets --features bedrock --
      -D warnings`, and `cargo test --locked --features bedrock`. `bedrock` is linted and
      tested, not merely compiled.
- [ ] AC-6: Every cargo invocation in every workflow that resolves dependencies carries
      `--locked`, including clippy, the release build in CI, and the publish dry run.
      A stale `Cargo.lock` fails the job instead of being rewritten.
- [ ] AC-7: `ci.yml` exposes a single non-matrix aggregator job named `CI Gate` that
      succeeds only when every matrix leg succeeded. This, not the matrix legs, is the
      context the ruleset requires, so adding or renaming an OS cannot silently change
      what is protected.
- [ ] AC-8: `release.yml` builds four targets on native runners - `x86_64-unknown-linux-gnu`
      on `ubuntu-22.04`, `aarch64-unknown-linux-gnu` on `ubuntu-22.04-arm`,
      `aarch64-apple-darwin` on `macos-latest`, `x86_64-apple-darwin` on `macos-15-intel` -
      with `cargo build --release --locked --target <triple>`. Runner labels are pinned to
      versions, never `-latest`, for anything whose output is distributed.
- [ ] AC-9: Each target is packaged as one `lok-<tag>-<target>.tar.gz` carrying both the
      `lok` and `lokomotiv` binaries plus `LICENSE`, with a `.sha256` sidecar, uploaded
      with `if-no-files-found: error`, and assembled into one GitHub Release by a second
      job.
- [ ] AC-10: `release.yml` rejects a tag that does not match
      `^v[0-9]+\.[0-9]+\.[0-9]+(-rc\.[0-9]+)?$`, that does not exist, that resolves to a
      commit unreachable from `main`, or whose version disagrees with `Cargo.toml`
      (base version only for `-rc.N`).
- [ ] AC-11: A tag ending in `-rc.N` produces a release marked `prerelease: true` and
      `make_latest: false`. A manually dispatched rehearsal produces `draft: true` and is
      never published, so a rehearsal cannot mutate or replace a public release.
- [ ] AC-12: Each built binary is smoke-tested on its native runner with `--version` and
      `--help` before upload, and each Linux binary is checked to require no `GLIBC_`
      symbol above the `ubuntu-22.04` baseline (2.35), with its dynamic dependencies
      (`libssl`, `libcrypto`) recorded in the job log.
- [ ] AC-13: `publish.yml` triggers only on `workflow_dispatch` with a required `tag`
      input, asserts tag-vs-`Cargo.toml` agreement, fails with an explicit message naming
      `CARGO_TOKEN` when the secret is absent, and runs `cargo publish --dry-run --locked`.
      It contains **no** real publish step. Both guards are documented as weak:
      `--dry-run` packages and compiles locally without authenticating to crates.io, and
      the token check is a presence assertion on the environment, not credential
      validation.
- [ ] AC-14: `main` carries an active ruleset targeting `refs/heads/main` that requires
      the `CI Gate` context from the GitHub Actions app, verified by reading
      `GET /repos/maxkulish/lok/rulesets/{id}` - the rule parameters themselves, not the
      list summary - and quoting the response in the PR.
- [ ] AC-15: The gate is demonstrated on this PR: with the ruleset active, the PR is
      observed blocked while `CI Gate` is pending or failing, and mergeable once it
      passes.
- [ ] AC-16: **After merge**, the `push` run on `main` is green. This is the criterion the
      Linear title is actually about, and it can only be verified post-merge; the workflow
      does not reach `complete` until it holds.

**Verification method**: §5. Note the ordering constraint that AC-14 through AC-16 encode:
`main` cannot be green on the new workflow before the PR merges, so protection is enabled
mid-PR (after CI passes on the branch, before merge) and the post-merge run on `main` is a
separate, later criterion.

## 3. Constraints

**Must**:
- Keep the two-stage `build` matrix -> `release` assembly structure from gcm's
  `release.yml`, so one runner failure cannot fragment a release.
- Use native runners per target. No cross-compilation toolchains.
- Pin runner labels by version (`ubuntu-22.04`, `ubuntu-22.04-arm`, `macos-15-intel`) in
  `release.yml`. `ubuntu-latest`/`macos-latest` stay only in `ci.yml`, where a floating
  image is a feature rather than an undeclared compatibility floor.
- Pass `--locked` on every dependency-resolving cargo invocation, without exception.
- Lint and test the `bedrock` feature, not just compile it.
- Establish the cause of the failing test from a captured diagnostic before changing any
  code to fix it.
- Prefer removing the race over containing it: the fix should make the failure mode
  impossible for every caller of `write_exec_script`, rather than requiring each new
  subprocess test to opt into a mutex.
- Pin the one third-party release action to a full commit SHA
  (`softprops/action-gh-release@3d0d9888cb7fd7b750713d6e236d1fcb99157228`, v3.0.2).

**Must-not**:
- Do not change `reqwest`'s TLS stack, feature flags, or any runtime dependency. The musl
  question was decided against for this task; a rustls migration is separate work with its
  own proxy and custom-CA verification.
- Do not publish anything to crates.io, and do not add a step that could. `publish.yml`
  ends at the dry run in this task. A real publish needs its own authorization, a
  protected GitHub environment, and verified crate ownership.
- Do not weaken the failing test - no removing the assertion, no widening the substring,
  no `#[ignore]`, no `--test-threads=1`.
- Do not add a retry to `probe_version` or any production path to paper over a
  test-harness race.
- Do not claim the workflows are "hardened" while every action floats on a mutable tag.
  Either the pinning policy below is followed or the claim is dropped.
- Do not let a release rehearsal create or overwrite a public release.

**Prefer**:
- One CI job per OS plus the aggregator, over lok's current three jobs that each restore
  their own cargo cache.
- Dropping `dtolnay/rust-toolchain` in favour of the runner's preinstalled `rustup`, as
  gcm does. That removes a third-party action from the trusted set rather than pinning it.
- Keeping first-party `actions/*` on `@v4` major tags; pinning is reserved for third-party
  actions, and the asymmetry is stated in the workflow rather than left implicit.
- Keeping `workflow_dispatch` on `ci.yml`, which commit `fed1246` added.

**Escalate when**:
- The captured diagnostic shows a cause outside the test harness - a `noexec` mount, or a
  genuine bug in `probe_version`'s timeout handling.
- The stress run cannot reproduce the failure in 20 iterations, leaving the fix unproven.
  Say so; do not declare AC-2 met on a green sample.
- `ubuntu-22.04-arm` does not resolve for this repo. **Stop and ask** - do not silently
  drop the target, because AC-8 requires four.
- Making the check required needs repository permissions or plan features beyond a ruleset
  write.
- Any criterion would need a change to `Cargo.toml`.

## 4. Decomposition

1. **Instrument the probe assertions** - every `assert!(...contains(...))` on a
   `diagnostic` in the gemini and codex probe tests gains a message printing the actual
   value, in the style already at `src/backend/gemini.rs:1296`.
   Files: `src/backend/gemini.rs`, `src/backend/codex.rs`.

2. **Reproduce, twice** - (a) a deterministic Linux-only test that builds the
   inherited-descriptor interleaving by hand and asserts the resulting `execve` behaviour,
   which turns the hypothesis into a checkable claim; (b) a full-suite parallel stress run
   on a Linux runner to capture the real diagnostic in situ. Quote it in the PR.
   Files: `src/backend/mod.rs` (test), `.github/workflows/ci.yml` (stress job).
   **Blocked by 1.**

3. **Remove the race at the helper** - `write_exec_script` materialises the script through
   a short-lived child process (body on the child's stdin, file opened for writing only by
   that child), so the calling process never holds a write descriptor that another
   thread's `fork` could inherit. The helper's contract is unchanged: it still returns a
   `tempfile::TempPath` whose drop deletes the script. The deterministic test from 2(a)
   flips red to green and becomes the regression guard. **Fallback**, only if the evidence
   points somewhere the helper cannot reach: extend `acquire_test_lock` across the six
   unguarded sites and reconcile `claude.rs`'s `PATH_LOCK` with `TEST_MUTEX` - and record
   that this is containment, not a fix.
   Files: `src/backend/mod.rs` (+ `gemini.rs`, `codex.rs`, `claude.rs` in the fallback).
   **Blocked by 2.**

4. **Rewrite `ci.yml`** - `build-and-test` over `[ubuntu-latest, macos-latest]` with
   `fail-fast: false`, one cargo cache keyed on `runner.os` + `Cargo.lock`; fmt, clippy,
   test, and the bedrock clippy+test pair, all `--locked`; then a `CI Gate` job with
   `needs: build-and-test`, `if: always()`, failing unless the matrix result is `success`.
   Triggers stay `push: [main]`, `pull_request`, `workflow_dispatch`.
   Files: `.github/workflows/ci.yml`.

5. **Add the stress job** - in `ci.yml`, named `etxtbsy-stress`, outside `CI Gate`'s
   `needs` so it can never satisfy the required context. It runs the full unit suite 20
   times on `ubuntu-latest` and fails on the first failure. Gated on
   `contains(github.event.pull_request.labels.*.name, 'ci-stress')` with
   `pull_request: types: [opened, synchronize, reopened, labeled]`, plus
   `workflow_dispatch`. The label path is what makes it runnable **pre-merge**: a
   `workflow_dispatch`-only job would need the file on the default branch first.
   Files: `.github/workflows/ci.yml`. **Blocked by 4.**

6. **Rewrite `release.yml`** - two-stage build/release, four pinned native runners, strict
   tag regex plus existence, reachability-from-`main` and `Cargo.toml` version assertions;
   `--version`/`--help` smoke test and the GLIBC-baseline check on each Linux binary;
   single per-target tarball with `.sha256`; assembly via the SHA-pinned
   `action-gh-release` with `generate_release_notes`, `fail_on_unmatched_files`,
   `overwrite_files`, and `draft`/`prerelease`/`make_latest` derived from the trigger and
   tag shape. `permissions: contents: read` on `build`, `contents: write` only on the
   assembly job.
   Files: `.github/workflows/release.yml`. **Independent of 1-5.**

7. **Rewrite `publish.yml`** - `workflow_dispatch` with a required `tag` input, checkout at
   that tag, the same version assertion, the `CARGO_TOKEN` presence guard, then
   `cargo publish --dry-run --locked`, and stop. `permissions: contents: read`. If a real
   publish is ever added, it must pass the secret explicitly via `--token` or map it to
   `CARGO_REGISTRY_TOKEN`, which is the variable cargo reads automatically -
   `CARGO_TOKEN` is not.
   Files: `.github/workflows/publish.yml`. **Independent of 1-6.**

8. **Protect `main`, then prove it** - in order: (a) CI green on the PR, note the exact
   `CI Gate` context; (b) create the ruleset via `gh api` with `enforcement: active`,
   target `refs/heads/main`, required status check `CI Gate` with the GitHub Actions
   `integration_id`, `strict_required_status_checks_policy: true`, and an empty
   `bypass_actors` list; (c) push to the PR branch and observe the merge blocked while the
   check is pending; (d) merge; (e) verify the post-merge `push` run on `main` is green.
   Record the exact API calls and the `GET /rulesets/{id}` response in the PR.
   **Blocked by 3 and 4.** Steps (d) and (e) belong to the PR and complete phases, not to
   implementation.

**Dependency order**: 1 -> 2 -> 3; 4 -> 5; (3, 4) -> 8. Sub-tasks 6 and 7 are independent.

**Edge cases to verify**:
- A `-rc.N` tag matches `Cargo.toml` on its base version only, and yields
  `prerelease: true`, `make_latest: false`.
- Re-running `release.yml` on a real tag updates assets in place. This is deliberately
  mutable, and the tradeoff is accepted here rather than hidden: checksums stored beside
  the artifacts they describe prove integrity of transfer, not authenticity of origin.
  Build provenance attestations are the answer to that and are recorded as follow-up, not
  smuggled into a CI task.
- macOS keeps passing the exec-script tests; the Linux fix must not regress it.
- `bedrock` clippy and tests pass on both OSes - the AWS SDK pulls a distinct tree.
- A fork PR runs CI with no secret exposure; nothing in `ci.yml` reads a secret.
- The `aarch64-unknown-linux-gnu` binary runs on its own runner, proving a native build.

**Assumptions to verify during implementation**:
- `ubuntu-22.04-arm` resolves for this repo. The label is current in
  `actions/runner-images`, and ARM runners are free for public repositories, but the first
  release run is the proof. If it does not resolve, escalate rather than dropping the
  target (AC-8 requires four).
- `macos-15-intel` is the current x86_64 macOS image; `macos-13` is retired. GitHub has
  announced x86_64 macOS sunset for August 2027, at which point `x86_64-apple-darwin`
  leaves the matrix rather than moving to cross-compilation.
- `gh workflow run --ref <branch>` runs the branch's copy of a workflow that already
  exists on `main` with `workflow_dispatch`, and accepts inputs declared only on the
  branch. `ci.yml` and `release.yml` qualify; `publish.yml` does not, since it has no
  `workflow_dispatch` on `main` today. If the API rejects branch-only inputs, release
  verification moves post-merge alongside publish.

**Out of scope, recorded as follow-up**:
- `Cargo.toml:9-10` still points `repository` and `homepage` at `github.com/ducks/lok`,
  which is not where this code lives. It matters only once something is really published,
  which this task explicitly does not do.
- Build provenance attestations for release artifacts.
- A rustls migration that would make static musl targets available.
